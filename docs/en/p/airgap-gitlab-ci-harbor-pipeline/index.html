GitLab CI and Harbor Registry Integration Pipeline Implementation for Air-Gapped Clusters

A build note for a GitLab CI/CD pipeline targeting an isolated network Kubespray cluster. Details the setup for internal Harbor integration, Dockerfile static validation, automatic tag generation, and blocking external communication by specifying --pull=false.

In air-gapped environments where internet connectivity is restricted or completely disconnected, outbound communication to external public registries (such as Docker Hub or Quay.io) is blocked by firewalls. When operating a Kubernetes cluster using Kubespray in such infrastructure, if container image dependency resolution includes public endpoints, the build pipeline will halt due to timeouts or name resolution errors. To ensure reproducibility in the container build process and eliminate unintended external network requests, a static validation gate with an internal private registry as a prerequisite and a pipeline configuration dedicated to isolated environments are essential.

This article outlines the implementation specifications of a GitLab CI/CD pipeline designed to securely generate, validate, and distribute workload images deployed to a Kubespray cluster, built upon the internal registry “Harbor”.

Overall Pipeline Architecture and Execution Base Parameters

In the target environment, the GitLab Runner itself is placed within the isolated network, constraining target nodes via the docker and offline execution tags. The global configuration used across the entire pipeline is as follows:

stages:
  - validate
  - build

variables:
  HARBOR_REGISTRY: "harbor.devstack.co.kr:8443"
  HARBOR_PROJECT: "kubespray"
  IMAGE_NAME: "nginx-app"

image: "$HARBOR_REGISTRY/$HARBOR_PROJECT/ci/docker:29.1.4-cli"

Configuration Parameter Specifications

  1. stages definition: Composed of validate (a static validation phase to inspect whether the Dockerfile in the repository correctly references the base image from the internal registry) and build (a phase that performs authentication against the internal Harbor, image tag generation based on commit metadata, container image build and push, and environment variable metadata output).

  2. variables definition: Specifies the private Harbor’s FQDN and TLS communication port (harbor.devstack.co.kr:8443) in HARBOR_REGISTRY, and sets the project namespace (kubespray) to isolate and store Kubespray artifacts in HARBOR_PROJECT. Additionally, defines the target workload container image name (nginx-app) in IMAGE_NAME.

  3. Execution image (image): The runner container itself does not rely on a public registry and is pulled from harbor.devstack.co.kr:8443/kubespray/ci/docker:29.1.4-cli. Pinning the version to 29.1.4-cli prevents build failures caused by behavioral discrepancies in CLI options.

Detailed Job Design by Stage

1. Dockerfile Static Validation Job (validate:dockerfile)

Before entering the build process, validate whether unauthorized FROM clauses referencing external registries have been introduced.

validate:dockerfile:
  stage: validate
  tags:
    - docker
    - offline
  script:
    - test -f Dockerfile
    - grep -q "$HARBOR_REGISTRY" Dockerfile
    - echo "Dockerfile validation passed"

💡 test -f Dockerfile verifies the existence of the Dockerfile in the root directory, and grep -q “$HARBOR_REGISTRY” Dockerfile inspects whether the base image reference line contains harbor.devstack.co.kr:8443. If a statement directly specifying an external repository (e.g., FROM nginx:latest) exists, the exit status becomes non-zero, immediately blocking subsequent build job execution.

2. Build and Registry Distribution Job (build:push)

Handles container builds, secure credentials delivery, physical suppression of external requests, and pipeline integration of dynamic metadata.

build:push:
  stage: build
  tags:
    - docker
    - offline
  before_script:
    - docker version
    - echo "$HARBOR_PASSWORD" | docker login "$HARBOR_REGISTRY" -u "$HARBOR_USER" --password-stdin
  script:
    - |
      if [ -n "$CI_COMMIT_TAG" ]; then
        IMAGE_TAG="$CI_COMMIT_TAG"
      else
        IMAGE_TAG="sha-$CI_COMMIT_SHORT_SHA"
      fi

      IMAGE_URI="$HARBOR_REGISTRY/$HARBOR_PROJECT/$IMAGE_NAME:$IMAGE_TAG"

      echo "IMAGE_TAG=$IMAGE_TAG"
      echo "IMAGE_URI=$IMAGE_URI"

      docker build --pull=false -t "$IMAGE_URI" .
      docker push "$IMAGE_URI"

      echo "IMAGE_TAG=$IMAGE_TAG" &gt; build.env
      echo "IMAGE_URI=$IMAGE_URI" &gt;&gt; build.env
  artifacts:
    reports:
      dotenv: build.env
    expire_in: 7 days
  rules:
    - if: '$CI_COMMIT_BRANCH == "master"'
    - if: '$CI_COMMIT_TAG'

Technical Implementation Highlights

🛠️ Credential Obfuscation: Uses echo “$HARBOR_PASSWORD” | docker login … –password-stdin to prevent password exposure via command-line arguments (plaintext output to process trees or Runner logs).

⚙️ Dynamic Tag Logic: When a release tag is created ($CI_COMMIT_TAG), that tag name is used directly. For branch commits, a unique immutable tag in the format sha-<short-hash> is assigned.

⚠️ External Communication Suppression Flag (–pull=false): Standard docker build may query the remote repository for the latest layer even if a local cache exists. Explicitly specifying –pull=false completely blocks delays and timeout errors caused by unnecessary external probe requests in an isolated environment.

📦 Variable Propagation to Downstream Pipelines: Outputs IMAGE_TAG and IMAGE_URI to the build.env file, passing them to subsequent deployment pipelines (such as Kubespray Playbook execution jobs) via GitLab’s artifacts:reports:dotenv feature.

Troubleshooting

Documents common failure modes and resolution steps encountered during CI execution in isolated network environments.

1. TLS/x509 Certificate Verification Error on Non-Standard Port (8443)

Failure Symptom: If Harbor uses port 8443 and is secured by a self-signed certificate from an internal private certificate authority (CA), executing docker login fails with the following error and halts the job:

Error response from daemon: Get "https://harbor.devstack.co.kr:8443/v2/": x509: certificate signed by unknown authority

Resolution Steps: Place the internal root CA certificate on the Docker daemon of the Runner host. Docker automatically references the path /etc/docker/certs.d/<registry-hostname:port>/ca.crt.

sudo mkdir -p /etc/docker/certs.d/harbor.devstack.co.kr:8443
sudo cp /path/to/internal-ca.crt /etc/docker/certs.d/harbor.devstack.co.kr:8443/ca.crt
sudo systemctl restart docker

2. Missing Base Layer Error When --pull=false Is Specified

Failure Symptom: If –pull=false is specified while the base image referenced in the Dockerfile does not exist in the local cache of the Runner host, the build fails as follows:

ERROR: failed to solve: harbor.devstack.co.kr:8443/kubespray/base-nginx:1.25: not found: image not present locally and --pull=false set

Resolution Steps: Add a step in before_script to pre-fetch the necessary base image from Harbor into the local pool before job execution, or explicitly preload the image prior to the initial build.

docker pull harbor.devstack.co.kr:8443/kubespray/base-nginx:1.25

Operational Notes

🛠️ GitLab Runner Tag Management: Ensure Runners in isolated environments are always assigned the docker and offline tags to maintain isolation and prevent build requests from being routed to shared Runners with internet connectivity.

⚠️ dotenv Artifact Expiration: Because expire_in: 7 days is configured, if building pipelines that re-reference metadata from historical jobs older than 7 days, consideration must be given to storing data in an external key-value store or implementing a commit-back mechanism to Git.

💡 Quota Management on Harbor: Untagged intermediate layers and old commit SHA images accumulate easily in Kubespray projects. Therefore, tag retention policies (e.g., retaining the last 20 tags or automatic cleanup after a specified period) must be configured on Harbor.
