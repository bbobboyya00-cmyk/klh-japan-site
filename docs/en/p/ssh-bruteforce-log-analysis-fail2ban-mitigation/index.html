SSH Brute-Force Attack Log Analysis and Building Dynamic Defense with Fail2ban in Linux Environments

Explains the construction of a Linux authentication log analysis pipeline, the implementation of an automated IP blocking mechanism using Fail2ban, and SSH hardening techniques.

The default SSH port (TCP 22) of Linux servers exposed to the internet is constantly subjected to dictionary attacks and brute-force attacks by automated botnets. In infrastructure operations where the number of nodes increases, manually updating firewall rules to block attacking IPs leads to human error and reaches its limit in terms of response speed.

This article outlines the configuration steps for building an authentication log analysis pipeline recorded in /var/log/auth.log and deploying an Intrusion Prevention System (IPS) that leverages Fail2ban to dynamically inject packet drop rules into netfilter (iptables).

Authentication Log Structure and Text Analysis Pipeline

In Debian/Ubuntu-based distributions, SSH authentication events are output to /var/log/auth.log (or /var/log/secure in RHEL/CentOS-based systems).

Attack Log Sample Trace

May 20 14:21:05 server-node sshd[4102]: Failed password for invalid user admin from 192.168.56.120 port 54321 ssh2
May 20 14:21:07 server-node sshd[4105]: Failed password for invalid user root from 192.168.56.120 port 54322 ssh2
May 20 14:21:09 server-node sshd[4108]: Failed password for root from 192.168.56.120 port 54323 ssh2
May 20 14:21:11 server-node sshd[4111]: Accepted password for deployer from 192.168.56.10 port 51100 ssh2

The Failed password pattern in the log indicates an authentication failure. When invalid user is included, it denotes an attempt using a username that does not exist in the local /etc/passwd; when it is not included, it signifies an attack against an existing account.

Extracting Attacking IPs via CLI Commands

To quickly identify top IP addresses with high attack frequencies from large log volumes, execute a pipeline combining standard Linux utilities.

grep "Failed password" /var/log/auth.log | awk '{for(i=1;i&lt;=NF;i++) if($i=="from") print $(i+1)}' | sort | uniq -c | sort -nr | head -n 10

Through awk loop processing, the field immediately following the from token is reliably extracted even when column positions vary depending on the presence of invalid user.

Automated Defense Configuration Using Fail2ban

Based on threat indicators detected via log analysis, dynamic blocking rules are applied using Fail2ban. To protect package default configuration files, create /etc/fail2ban/jail.local to override definitions.

[sshd]
enabled  = true
port     = ssh
filter   = sshd
logpath  = /var/log/auth.log
maxretry = 5
findtime = 10m
bantime  = 1h

💡 Key Parameter Definitions:

・maxretry: The maximum number of failed attempts permitted within the specified timeframe.

・findtime: The time window for counting failed attempts (10 minutes in the configuration above).

・bantime: The duration for blocking packets once conditions are met (1 hour in the configuration above).

Defense-in-Depth Configuration for SSH Service

In addition to deploying an IPS, optimize the configuration of the SSH daemon itself (/etc/ssh/sshd_config) to reduce the attack surface.

  1. Change Port Number: Change from the default port 22 to a high-numbered port (e.g., 22022) to reduce exposure to wide-area scanners.

  2. Disable Direct Root Login: Set PermitRootLogin no to block direct access attempts as a privileged user.

  3. Disable Password Authentication: Set PasswordAuthentication no to allow only public key authentication, eliminating dictionary attacks.

Troubleshooting

Common troubleshooting scenarios and countermeasures encountered when deploying Fail2ban.

1. Log Path Identification Issues in systemd Environments

In environments such as Ubuntu 22.04 and later or systems where rsyslog is disabled by default, /var/log/auth.log may not be generated, causing Fail2ban startup to fail.

⚠️ Symptom: The error Have not found any log file for sshd jail occurs upon starting fail2ban.service.

🛠️ Solution: Explicitly specify backend = systemd in the [sshd] section of /etc/fail2ban/jail.local to configure Fail2ban to read logs directly from journald.

2. iptables/nftables Backend Conflicts

Depending on the OS kernel version, the packet filter backend (iptables-legacy vs nftables) may differ, causing BAN rules to fail to inject correctly.

🛠️ Solution: Execute fail2ban-client status sshd. If traffic still passes despite the IP being listed in Banned IP list, switch banaction in /etc/fail2ban/jail.conf from iptables-multiport to nftables or nftables-multiport.
