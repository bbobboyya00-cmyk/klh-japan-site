Building a Robust Backup Architecture Using an Append-Only Model

Operating various Docker containers (PostgreSQL, Redis, Qdrant), automation pipelines, and system configurations on a single NVMe storage drive on a single Linux Mini PC host carries a constant risk of data loss due to hardware degradation or filesystem corruption. To safely maintain dynamic operational data beyond source code, a backup architecture that eliminates single points of failure (SPOF) is essential.

This article details the setup procedures for an “Append-Only” backup architecture from a primary server to a network NAS (Synology DS923+). This design guarantees application-layer transaction consistency while preventing backdated deletion or tampering of backup data even if the host is compromised.

Architecture Comparison and Selection Background

When offloading data from a Linux host, approaches such as Synology Active Backup for Business (ABB), rsync, BorgBackup, and restic are considered. However, careful evaluation is required regarding kernel compatibility and security boundaries.

Synology ABB Linux Agent: Relies on a proprietary kernel module (synosnap). In a Debian 13 (Linux Kernel 6.12) environment, there is a high risk of kernel panics or build failures during automatic updates, and it lacks mechanisms to prevent database inconsistency.

rsync over SSH/SMB: Allows simple synchronization, but lacks client-side encryption, deduplication, and point-in-time version management. Furthermore, if the host side is infected with ransomware, synchronized remote files risk being overwritten with encrypted data.

BorgBackup: Provides advanced deduplication and encryption, but requires executing third-party binaries on the DSM side, and concerns have been raised regarding bypass vectors for Append-Only restrictions.

restic + rest-server (Selected): Runs the lightweight single binary restic on the client side, and launches the official rest-server in containerized --append-only mode on the NAS side. Under this configuration, DELETE and file truncation requests are rejected (403 Forbidden) at the HTTP API level, preserving historical backup snapshots even if root access on the primary server is compromised.

Step 1: Synology NAS Setup

1. Creating a Btrfs Shared Folder

Navigate to DSM Control Panel -> Shared Folder -> Create, name it server-backup, and select the Btrfs storage pool. Disable the Recycle Bin since restic manages objects internally, and check Enable data checksum for advanced data integrity, which is required for Btrfs silent data corruption detection. Volume encryption is disabled to prevent performance degradation from double encryption, as restic handles AES-256 client-side encryption.

2. Configuring Immutable Snapshots with Snapshot Replication

Open DSM Snapshot Replication and configure a schedule for the server-backup folder to run every Saturday at 06:00. Set the retention policy to 8 generations and enable Immutable Snapshots for 7 days. This ensures that even if the NAS administrator account is compromised, data deletion is physically impossible for a set duration.

3. Deploying Container Manager (rest-server)

Pull the restic/rest-server:latest image from Container Manager and launch the container with the --append-only option enabled. Generate user authentication accounts and verify API connectivity.

version: '3.8'
services:
  rest-server:
    image: restic/rest-server:latest
    container_name: rest-server
    restart: always
    ports:
      - "8000:8000"
    volumes:
      - /volume2/server-backup:/data
    environment:
      - OPTIONS=--append-only
      - PASSWORD_FILE=/data/.htpasswd
