インフラストラクチャの運用において、「Pingは通るが、サーバーへの接続（SSHやHTTPなど）が失敗する」という事象は頻繁に発生します。ICMPによるL3レベルの疎通確認のみに依存し、L4以上のトランスポート層やL7アプリケーション層の検証を怠ることは、障害復旧の遅延や誤った原因特定を招く要因となります。

ICMPエコーテストは低レイテンシかつパケットロス0%で成功している状態を示します。

```bash
$ ping 192.168.10.100
PING 192.168.10.100 (192.168.10.100) 56(84) bytes of data.
64 bytes from 192.168.10.100: icmp_seq=1 ttl=64 time=0.3 ms
64 bytes from 192.168.10.100: icmp_seq=2 ttl=64 time=0.2 ms
```

しかし、SSHセッションやHTTPリクエストを開始すると、接続に失敗します。

```bash
$ ssh 192.168.10.100
ssh: connect to host 192.168.10.100 port 22: Connection refused
```

あるいは、接続試行時にタイムアウトが発生します。

```bash
$ curl http://192.168.10.100:8080
curl: (7) Failed to connect to 192.168.10.100 port 8080: Connection timed out
```

「Pingが成功したためネットワークは正常であり、接続失敗はサーバー自体の破損を意味する」という仮定は、技術的に誤りです。ICMPはネットワーク層（L3）で動作するのに対し、SSH、HTTP、HTTPS、PostgreSQL、MySQL、Redisなどの主要なアプリケーションプロトコルは、特定のポート番号にバインドされたトランスポート層（L4）のTCPソケットに依存しているためです。

本稿では、この境界ギャップを体系的に分解し、Linuxの3つのコアユーティリティである `ss`、`nc`、`tcpdump` を中心とした診断手法を確立します。

## 1. ネットワーク層の抽象化とサービスマッピング

💡 通信のボトルネックを効果的に特定するために、対象サービスをOSI参照モデルの各レイヤーとトランスポートメカニズムにマッピングします。

* <b>ICMP</b>: `ping` などの診断および制御メッセージングにのみ使用されます（トランスポートポートは存在しません）。
* <b>SSH</b>: TCP ポート `22`
* <b>HTTP</b>: TCP ポート `80`
* <b>HTTPS</b>: TCP ポート `443`
* <b>PostgreSQL</b>: TCP ポート `5432`
* <b>MySQL / MariaDB</b>: TCP ポート `3306`
* <b>Redis</b>: TCP ポート `6379`

ICMPはL4のTCPリスニングソケットとは独立して動作するため、ICMPエコーリクエストに対する応答があっても、TCPポートが開放されている、あるいは到達可能である保証はありません。

## 2. `ping` の低レイヤーメカニズム

`ping 192.168.10.100` を実行すると、宛先ホストに対して <b>ICMP Echo Request</b> パケット（Type 8）が送信され、宛先ホストは <b>ICMP Echo Reply</b> パケット（Type 0）を返します。

```text
+------------------------+                             +------------------------+
| Client: 192.168.10.50  |                             | Server: 192.168.10.100 |
+------------------------+                             +------------------------+
            |                                                      |
            |------------ ICMP Echo Request (Type 8) -------------&gt;|
            |                                                      |
            |&lt;----------- ICMP Echo Reply (Type 0) ----------------|
            |                                                      |
```

Ping of 成功は、クライアントからローカルルーティング、ゲートウェイ、物理ネットワーク、ターゲットのIPスタックを経て、ICMP応答が戻るパスが正常であることを確認するに留まります。ファイアウォールルールがTCPフレームを許可しているか、あるいはホスト上のアプリケーションデーモンがアクティブにソケットを処理しているかは検証できません。

## 3. TCP 3-Way ハンドシェイクの構造

TCPベースのサービス接続を開始する際、オペレーティングシステムのカーネルは、まず <b>TCP 3-Way ハンドシェイク</b> を介してステートフルな接続を確立する必要があります。

```text
Client (192.168.10.50)                                   Server (192.168.10.100:22)
      |                                                              |
      |----------------------- 1. SYN ------------------------------&gt;|
      |                                                              |
      |&lt;------------------- 2. SYN-ACK ------------------------------|
      |                                                              |
      |----------------------- 3. ACK ------------------------------&gt;|
      |                                                              |
[ ESTABLISHED ]                                                [ ESTABLISHED ]
```

1. <b>SYN</b>: クライアントは接続開始を要求するために、`SYN` フラグを設定したTCPフレームを送信します。
2. <b>SYN-ACK</b>: サーバーは `SYN` を受信すると、ポート `22` でリスニングしているソケットを確認し、接続状態バッファを割り当てて `SYN-ACK` で応答します。
3. <b>ACK</b>: クライアントは `ACK` で応答し、両方のエンドポイントが `ESTABLISHED` 状態に移行します。

アプリケーションプロトコルが機能するためには、このL4シーケンスが正常に完了する必要があります。

## 4. 「Ping疎通可能 ＋ TCP接続失敗」の診断

初期の診断状態を定義します。

```bash
$ ping 192.168.10.100
# 成功 (パケットロス 0%)

$ nc -zv 192.168.10.100 22
# 失敗
```

この不一致により、障害ドメインを即座に絞り込むことができます。ICMPが機能していることはL3ルーティングと物理リンクが正常であることを示し、TCPの失敗はL4ソケット、ファイアウォール、またはサービスデーモンの障害を示します。

## 5. `nc` (Netcat) によるトランスポート層のプロービング

Netcat (`nc`) は、TCPおよびUDPの接続アナライザーとして機能します。実務環境における主なユースケースは、特定のソケットアドレスに対する生のTCP到達性を検証することです。

Netcatの実行には、ポートスキャン用のオプションを指定します。

```bash
$ nc -zv 192.168.10.100 22
```

-z`: Zero-I/Oモード（ペイロードデータを送信せずにリスニングデーモンをスキャン）。
* `-v`: 詳細出力モード。

接続テストの実行結果から、ネットワークの状態を判定します。

1. <b>ハンドシェイク成功</b>:

   ```text
   Connection to 192.168.10.100 22 port [tcp/ssh] succeeded!
   ```

2. <b>失敗パターン A</b>:

   ```text
   nc: connect to 192.168.10.100 port 22 failed: Connection refused
   ```

3. <b>失敗パターン B</b>:

   ```text
   nc: connect to 192.168.10.100 port 22 failed: Connection timed out
   ```

<b>Connection Refused</b> と <b>Connection Timed Out</b> の違いを理解することは、根本原因の特定において極めて重要です。

## 6. Connection Refused と Connection Timeout のメカニズム

### Connection Refused の仕組み

⚠️ `Connection refused` エラーは、クライアントの `SYN` パケットが宛先ホストのカーネルに到達したものの、ホストが明示的に接続を拒否し、TCP <b>Reset (`RST`)</b> フレームを返したことを示します。

```text
Client                                                       Server
  |                                                             |
  |--------------------------- SYN ----------------------------&gt;| (宛先ホストに到達)
  |                                                             | (リスニング中のプロセスなし)
  |&lt;------------------------ TCP RST ---------------------------|
```

#### 主な原因:

1. <b>サービスデーモンの停止</b>: プロセス（`sshd`、`nginx`、`mysqld` など）が起動していません。
2. <b>誤ったサービスポート</b>: アプリケーションがデフォルト以外のポート（例：`22` ではなく `2222`）でリスニングしています。
3. <b>バインドインターフェースの不整合</b>: デーモンが `0.0.0.0` ではなく `127.0.0.1` のみにバインドされています。
4. <b>アクティブなパケットフィルタリング</b>: ローカルホストのファイアウォールが、パケットを破棄（DROP）するのではなく、明示的にTCP Resetパケットを返す（REJECT）ように設定されています。

### Connection Timeout の仕組み

`Connection timed out` エラーは、クライアントが `SYN` パケットを送信したものの、ソケットのタイムアウトしきい値が経過するまでに<b>応答が一切返ってこなかった</b>場合に発生します。

```text
Client                                                   Network / Firewall / Target
  |                                                             |
  |--------------------------- SYN ----------------------------&gt;|
  |                                                             | ===&gt; [ 破棄 / ブロック ]
  |                     (応答なし)                              |
  | ... タイムアウト ...                                        |
```

#### 主な原因:

1. <b>ネットワークセキュリティによる破棄</b>: クラウドのセキュリティグループ、ネットワークACL、またはハードウェアファイアウォールがインバウンドトラフィックをサイレントに破棄しています。
2. <b>ホストレベルのファイアウォールによる破棄</b>: `iptables`、`firewalld`、または `nftables` が `DROP` アクションで設定されています。
3. <b>ルーティング障害</b>: 中間ネットワークスイッチやルーターにおけるデフォルトルーティングの誤り、または静的ルートの欠落。
4. <b>非対称ルーティング / 戻りパスの失敗</b>: サーバーは `SYN` を受信して `SYN-ACK` を送信したものの、戻りパスのルーティングでパケットが破棄または誤送信されています。

## 7. `ss` によるローカルソケットの検査

`ss` (Socket Statistics) ユーティリティは、Linuxプラットフォーム上のアクティブな内部ソケットを検査し、従来の `netstat` ツールに代わるものとして使用されます。

ソケットの状態を確認するための診断コマンドを実行します。

```bash
$ sudo ss -lntp
```

#### フラグ仕様:

* `-l`: リスニング（`LISTEN`）状態のソケットのみを表示。
* `-n`: 数値アドレスとポートを表示（DNSやサービス名の解決によるオーバーヘッドを防止）。
* `-t`: TCPソケットを表示。
* `-p`: ソケットに関連付けられたプロセスIDと名前を表示（`root` または `sudo` 権限が必要）。

コマンドの実行により、以下のようなソケット情報が出力されます。

```text
State      Recv-Q Send-Q  Local Address:Port  Peer Address:Port  Process
LISTEN     0      128           0.0.0.0:22         0.0.0.0:*      users:(("sshd",pid=1234,fd=3))
LISTEN     0      128           0.0.0.0:80         0.0.0.0:*      users:(("nginx",pid=1500,fd=6))
LISTEN     0      128         127.0.0.1:8080       0.0.0.0:*      users:(("java",pid=2000,fd=20))
```

## 8. バインドアドレスの分析: `127.0.0.1` vs `0.0.0.0`

`Local Address:Port` のバインド設定は、外部からの到達性を決定します。

### ループバック隔離ケース (`127.0.0.1:8080`)

ソケットがループバックアドレスにのみバインドされている状態を示します。

```text
LISTEN  0  128  127.0.0.1:8080  0.0.0.0:*
```

アプリケーションプロセス（`java`）は <b>ループバックインターフェース（`lo`）</b> にのみバインドされています。

```text
[ 外部クライアント ]                                [ ターゲットサーバー ]
  192.168.10.50                                      192.168.10.100
        |                                                  |
        |--- 192.168.10.100:8080 へのHTTPリクエスト ------&gt;| [ 物理インターフェース ]
                                                           |       |
                                                           |   (ブロック / ソケットなし)
                                                           |       v
                                                           | [ ループバックインターフェース ]
                                                           |   127.0.0.1:8080 (Javaデーモン)
```

<b>ローカル検証</b>: サーバー上で `curl http://127.0.0.1:8080` を実行すると成功します。
* <b>リモート検証</b>: 外部クライアントから `curl http://192.168.10.100:8080` を実行すると失敗します。

### ワイルドカードIPv4バインド (`0.0.0.0:8080`)

ソケットがすべてのインターフェースにバインドされている状態を示します。

```text
LISTEN  0  128  0.0.0.0:8080  0.0.0.0:*
```

ソケットは、ホストに割り当てられた<b>すべてのアクティブなIPv4ネットワークインターフェース</b>（例：IP `192.168.10.100` を持つ `ens160`）を介したインバウンドTCPトラフィックを受け入れます。ファイアウォールが許可していれば、外部クライアントからの接続が可能です。

```text
+-------------------------------------------------------------+
| Server: 192.168.10.100                                      |
|                                                             |
| Interface ens160 [ 192.168.10.100 ] &lt;--- [ 外部リクエスト ]  |
|          |                                                  |
|          v                                                  |
| 0.0.0.0:8080 にバインドされたサービス (全インターフェースで受診) |
+-------------------------------------------------------------+
```

## 9. 実務におけるトラブルシューティング事例

### 事例 1: Pingは通るが、SSHが失敗する (`Connection Refused`)

#### 環境構成:

* <b>クライアント</b>: `192.168.10.50`
* <b>サーバー</b>: `192.168.10.100`
* <b>対象サービス</b>: SSH (TCP ポート `22`)

#### ステップ 1: クライアント側での診断

```bash
$ ping 192.168.10.100
# 結果: 64 bytes from 192.168.10.100: icmp_seq=1 ttl=64 time=0.3 ms (成功)

$ nc -zv 192.168.10.100 22
# 結果: nc: connect to 192.168.10.100 port 22 failed: Connection refused
```

#### ステップ 2: サーバー側でのソケット検査

サーバーのローカルコンソールまたは帯域外（OOB）管理インターフェースにログインします。

```bash
$ sudo ss -lntp
# 出力結果:
# LISTEN 0 128 0.0.0.0:80 0.0.0.0:* users:(("nginx",pid=1500,fd=6))
```

TCPポート22がリスナーテーブルに存在しません。*

#### ステップ 3: サービス状態の確認と解決

```bash
$ sudo systemctl status sshd
# 出力: Active: inactive (dead)

$ sudo systemctl start sshd
$ sudo systemctl enable sshd

$ sudo ss -lntp | grep ':22'
# 出力: LISTEN 0 128 0.0.0.0:22 0.0.0.0:* users:(("sshd",pid=3102,fd=3))
```

クライアント側で再度 `nc -zv 192.168.10.100 22` を実行すると、接続が成功します。

---

### 事例 2: プロセスは起動しているが、外部アクセスが失敗する (`Bind Mismatch`)

#### 診断状態:

アプリケーションサーバー上で `ss -lntp` を実行すると、以下の結果が得られます。

```text
LISTEN 0 128 127.0.0.1:8080 0.0.0.0:* users:(("node",pid=4211,fd=18))
```

#### 疎通テスト:

* <b>ターゲットサーバーから</b>: `curl http://127.0.0.1:8080` $\longrightarrow$ <b>200 OK</b>
* <b>リモートクライアントから</b>: `curl http://192.168.10.100:8080` $\longrightarrow$ <b>接続拒否 (Refused)</b>

#### 診断と解決策:

アプリケーション（Node.js、Spring Boot、Nginxなど）の設定が `localhost` に制限されています。ホストの設定（例：`server.host = 0.0.0.0` または `LISTEN 0.0.0.0:8080`）を変更し、サービスを再起動してソケットを外部インターフェースに公開します。

---

### 事例 3: サービスはバインドされているが、外部接続がタイムアウトする

#### 診断状態:

サーバーのソケットテーブルは正常に公開されています。

```bash
$ sudo ss -lntp | grep ':8080'
LISTEN 0 128 0.0.0.0:8080 0.0.0.0:* users:(("java",pid=8820,fd=7))
```

しかし、クライアント側での実行は失敗します。

```bash
$ nc -zv 192.168.10.100 8080
nc: connect to 192.168.10.100 port 8080 failed: Connection timed out
```

#### ファイアウォールの検査:

出力が `Refused` ではなく `Timeout` であるため、インラインネットワークデバイスまたはホストのファイアウォールルールがパケットをサイレントに破棄しています。

ローカルホストのルールを確認します。

```bash
$ sudo firewall-cmd --list-all
# サービスおよびポートセクションに '8080/tcp' が存在するか確認

$ sudo nft list ruleset
```

firewalld` でICMPがグローバルに許可されていても、ポート8080が除外されている場合、`ping` は通過しますが、ポート8080へのL4 TCPトラフィックは破棄されます。

```text
Client (192.168.10.50)                                   Server (192.168.10.100)
      |                                                             |
      |----------------------- TCP SYN ----------------------------&gt;|
      |                                                             |
      |                                              [ Host Firewall (nftables) ]
      |                                              [ Action: DROP Port 8080   ]
      |                                                             |
      | &lt;=== Timeout (SYN-ACKが送信されない) ========================|
```

## 10. `tcpdump` によるディープパケット診断

`nc` は接続結果を報告し、`ss` はソケットのリスニング状態を示します。しかし、`tcpdump` は実際のパケットの動きをキャプチャし、フレームレベルでの状態遷移を明らかにします。

ターゲットサーバーでパケットキャプチャを実行します。

```bash
$ sudo tcpdump -nn -i ens160 tcp port 8080
```

-n`: ホスト名を解決しない。
* `-nn`: ホスト名およびポート名を解決しない（数値IPとポートを表示）。
* `-i ens160`: 対象ネットワークインターフェース `ens160` のトラフィックを監視。
* `tcp port 8080`: ポート8080を通過するTCPパケットのみをフィルタリング。

## 11. `tcpdump` によるパケットパターンの分析

### シナリオ A: 正常な TCP 3-Way ハンドシェイク

```text
10:00:01.001 IP 192.168.10.50.52344 &gt; 192.168.10.100.8080: Flags [S], seq 1001
10:00:01.002 IP 192.168.10.100.8080 &gt; 192.168.10.50.52344: Flags [S.], seq 2001, ack 1002
10:00:01.003 IP 192.168.10.50.52344 &gt; 192.168.10.100.8080: Flags [.], seq 1002, ack 2002
```

Flags [S]`: クライアントからの初期 SYN フレーム。
* `Flags [S.]`: サーバーからの SYN-ACK 応答。
* `Flags [.]`: クライアントからの ACK フレーム。
* <b>診断</b>: L4ハンドシェイクが完了し、接続が確立（ESTABLISHED）されています。

### シナリオ B: 応答のないインバウンド SYN の継続

```text
10:00:01.001 IP 192.168.10.50.52344 &gt; 192.168.10.100.8080: Flags [S], seq 1001
10:00:04.005 IP 192.168.10.50.52344 &gt; 192.168.10.100.8080: Flags [S], seq 1001
10:00:10.009 IP 192.168.10.50.52344 &gt; 192.168.10.100.8080: Flags [S], seq 1001
```

<b>観察</b>: クライアントが TCP `SYN` を再送信しています。サーバーのインターフェースはパケットを受信していますが、アウトバウンドの `SYN-ACK` (`[S.]`) が送信されていません。
* <b>診断</b>: ホストレベルのセキュリティメカニズム（`iptables`、`nftables`、`SELinux`、またはカーネルレベルのIPフィルタリング）が、ネットワークインターフェース層への流入直後にパケットを破棄しています。

### シナリオ C: サーバーは SYN-ACK を送信するが、クライアントが SYN を再送する

```text
10:00:01.001 IP 192.168.10.50.52344 &gt; 192.168.10.100.8080: Flags [S]
10:00:01.002 IP 192.168.10.100.8080 &gt; 192.168.10.50.52344: Flags [S.]
10:00:04.005 IP 192.168.10.50.52344 &gt; 192.168.10.100.8080: Flags [S]
```

<b>観察</b>: サーバーはインバウンド `SYN` を処理して `SYN-ACK` を送信していますが、クライアントは応答を受信していないかのように `SYN` フレームを送信し続けています。
* <b>診断</b>: サーバーとクライアント間の<b>戻りパスのルーティング障害</b>、または送信元方向へのエグレスファイアウォールによるフィルタリングが発生しています。

```text
Client (192.168.10.50)                                   Server (192.168.10.100)
      |                                                             |
      |----------------------- 1. SYN -----------------------------&gt;|
      |                                                             |
      | X &lt;=== [ 戻りルーティング障害 / エグレスブロック ] ---------| (SYN-ACKを送信)
```

主な原因：
1. ターゲットサーバー上のローカルデフォルトゲートウェイの設定誤り。
2. 非対称ルーティングポリシーによる戻りパスの破棄。
3. NATテーブルの状態喪失。

### シナリオ D: 即時のリセット (`SYN` 直後の `RST`)

```text
10:00:01.001 IP 192.168.10.50.52344 &gt; 192.168.10.100.8080: Flags [S]
10:00:01.001 IP 192.168.10.100.8080 &gt; 192.168.10.50.52344: Flags [R.]
```

<b>観察</b>: サーバーが即座にリセットフレーム（`[R.]`）を返しています。
* <b>診断</b>: パケットはホストのファイアウォールを通過しましたが、カーネルは TCP ポート 8080 でリスニングしているプロセスを見つけられませんでした。`ss -lntp` でデーモンの状態を確認してください。

## 12. カーネルカウンタによるソケット状態の追跡

`ss -ant` を実行して、アクティブなソケット全体の接続状態の割り当てを確認します。

```bash
$ sudo ss -ant
State      Recv-Q Send-Q  Local Address:Port  Peer Address:Port
LISTEN     0      128     0.0.0.0:8080        0.0.0.0:*
ESTAB      0      0       192.168.10.100:8080 192.168.10.50:52344
SYN-RECV   0      0       192.168.10.100:8080 192.168.10.50:52345
```

### 重要なソケット状態と異常値:

1. <b>`SYN-SENT` の累積 (クライアント側)</b>:

   ```bash
   $ ss -ant state syn-sent
   ```

意味*: クライアントアプリケーションが `SYN` フレームを送信しましたが、`SYN-ACK` を受信していません。アウトバウンドのブロックまたは経路上の破棄を示します。

2. <b>`SYN-RECV` の累積 (サーバー側)</b>:

   ```bash
   $ ss -ant state syn-recv
   ```

意味*: サーバーが `SYN` を受信して `SYN-ACK` を送信しましたが、クライアントからの最終的な `ACK` を待機したまま停止しています。クライアント側のインバウンドブロック、非対称ルーティング、またはSYNフラッド攻撃を示します。

## 13. 上位レイヤーの診断: PingとTCPは成功するが、アプリケーションが失敗する

さらに高度な障害状態を定義します。

```bash
$ ping 192.168.10.100
# 成功 (L3正常)

$ nc -zv 192.168.10.100 8080
# 成功 (L4 TCP接続正常)

$ curl http://192.168.10.100:8080/
# 失敗 / エラー / HTTP 5xx / 応答なし
```

このシナリオは、ネットワーク層（L3）およびトランスポート層（L4）が完全に機能していることを証明しています。

### `curl` によるアプリケーション層のデバッグ

詳細なHTTP操作を実行して、ハンドシェイクとプロトコルのセマンティクスをキャプチャします。

```bash
$ curl -v http://192.168.10.100:8080/
```

詳細な実行トレースの例を示します。

```text
*   Trying 192.168.10.100:8080...
* Connected to 192.168.10.100 (192.168.10.100) port 8080 (#0)
&gt; GET / HTTP/1.1
&gt; Host: 192.168.10.100:8080
&gt; User-Agent: curl/7.76.1
&gt; Accept: */*
&gt;
&lt; HTTP/1.1 504 Gateway Timeout
&lt; Server: nginx/1.20.1
&lt; Date: Mon, 10 Nov 2025 10:00:00 GMT
&lt; Content-Type: text/html
```

#### L7障害の主な原因カテゴリ:

1. <b>リバースプロキシの上流タイムアウト</b>: Nginxはポート8080で接続を受け入れますが、ローカルで動作するバックエンド（例：`127.0.0.1:8000` のNode/Javaアプリ）への到達に失敗し、HTTP `504 Gateway Timeout` または `502 Bad Gateway` を返します。
2. <b>HTTPホストヘッダーの拒否</b>: アプリケーションの仮想ホストフィルタが、有効な `Host:` リクエストヘッダーを欠くリクエストを破棄しています。
3. <b>アプリケーションのスレッドロック</b>: データベース接続プールの枯渇や内部デッドロックにより、L4ソケットハンドシェイクが確立されているにもかかわらず、アプリケーション層がペイロードフレームを送信できません。
4. <b>TLS/SSLハンドシェイクの失敗</b>: 暗号スイートの不一致、証明書の期限切れ、またはSNIの誤設定により、ポート443でのTCP初期化直後に接続が切断されます。

## 14. UDPプロトコル診断における注意点

TCPとは異なり、<b>UDPはコネクションレス</b>です。セットアップフラグ（`SYN`、`ACK`）や状態マシンのチェックはありません。

`nc` を使用してUDPの到達性をテストするには、`-u` フラグが必要です。

```bash
$ nc -zvu 192.168.10.100 53
```

### 診断上の課題:

* UDPスキャナーは0バイトのパケットを送信します。`ICMP Port Unreachable` フレームが戻ってこない場合、`nc` はポートが「開いている」または「開いているかフィルタされている」と判断します。
* 誤検知が非常に多いため、信頼性の高いUDPテストには、アクティブなパケットキャプチャと並行して、プロトコル固有のクエリツール（例：DNS UDP 53には `dig`、SNMP UDP 161には `snmpwalk`）を使用する必要があります。

```bash
$ sudo tcpdump -nn -i ens160 udp port 53
```

## 17. 運用CLIクイックリファレンス

### L3 診断コマンド:

```bash
# リンク到達性をテストするために4つのICMPパケットを送信
$ ping -c 4 192.168.10.100
```

### L4 ソケットプロービングコマンド (`nc`):

```bash
# 標準的な管理およびWebサービスのTCPポートを調査
$ nc -zv 192.168.10.100 22
$ nc -zv 192.168.10.100 80
$ nc -zv 192.168.10.100 443
$ nc -zv 192.168.10.100 8080

# UDPドメイン名解決サービスを調査
$ nc -zvu 192.168.10.100 53
```

### ローカルソケット検査コマンド (`ss`):

```bash
# プロセス詳細を含むすべてのアクティブなリスニングTCPポートを一覧表示
$ sudo ss -lntp

# 特定のターゲットソケットリスナーをフィルタリング
$ sudo ss -lntp | grep ':8080'

# 状態に関係なく、すべての数値TCP接続を表示
$ sudo ss -ant

# SYN-SENTまたはSYN-RECV状態の接続を分離
$ sudo ss -ant state syn-sent
$ sudo ss -ant state syn-recv
```

### パケット分析コマンド (`tcpdump`):

```bash
# 特定のインターフェースでTCPポート8080を監視
$ sudo tcpdump -nn -i ens160 tcp port 8080

# 生のSYN接続初期化リクエストをグローバルにキャプチャ
$ sudo tcpdump -nn -i ens160 'tcp[tcpflags] &amp; tcp-syn != 0'

# 特定のホストIPアドレスに関連するすべてのトラフィックをキャプチャ
$ sudo tcpdump -nn -i ens160 host 192.168.10.50

# ICMP制御パケットとターゲットTCPアプリケーショントラフィックを多重追跡
$ sudo tcpdump -nn -i ens160 'tcp port 8080 or icmp'
```

### ホストファイアウォール操作 (`firewalld` / `nftables`):

```bash
# 現在のfirewalld設定を検査
$ sudo firewall-cmd --list-all

# TCP 8080の許可を永続的に追加
$ sudo firewall-cmd --add-port=8080/tcp --permanent
$ sudo firewall-cmd --reload

# 低レベルのnftablesルールセットバインディングを検査
$ sudo nft list ruleset
```

## Lessons Learned

1. <b>Pingの成功はサービスの健全性を保証しない</b>: ICMP Echo応答は、レイヤー3のインターフェース到達性とルーティングの正常性のみを証明します。レイヤー4のポート状態やレイヤー7のアプリケーション機能は検証されません。
2. <b>エラーメッセージの正確な解釈</b>: 
* `Connection refused` は、パケットがホストに到達したものの、アクティブなリスナーがないか、明示的に `RST` 拒否されたことを示します。<b>ホストのソケットバインド</b> (`ss -lntp`) を確認してください。
* `Connection timed out` は、送信または戻りの経路でフレームが消失したことを示します。<b>ファイアウォール、セキュリティグループ、ルーティングループ</b>を確認してください。
3. <b>ワイヤキャプチャによるパケットパスの追跡</b>: `tcpdump` を使用して、「初期SYNフレームがインフラストラクチャスタックのどこまで到達したか」という根本的な問いに答えます。
4. <b>レイヤー範囲の段階的な分離</b>: L3（`ping`）からL4（`nc`）へ順次テストし、ローカルのリスニング状態（`ss`）を検査し、ワイヤ上の生のフレーム（`tcpdump`）を検証し、最後にL7（`curl`）で確認を行います。</service></port></port></ip></port></nic></port></server_ip>
